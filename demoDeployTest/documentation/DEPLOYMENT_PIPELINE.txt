1. SUMMARY
----------
When a pull request is merged into main, a GitHub Actions workflow finds
the Salesforce components that changed, builds a package.xml for only those
components using sfdx-git-delta (sgd), validates the deployment against the
target org (dry run), and then deploys it.

the target org. Validation and deployment both succeeded. All 4 Apex tests
pass and BedrockRequestPriorityService has 100% code coverage.

4. HOW THE WORKFLOW WORKS
-------------------------
Trigger: a pull request into main is closed AND merged. Closing a pull
request without merging does nothing.

Checkout ............ Checks out the merge commit with full git history.
Node.js ............. Installs Node 24 (the Salesforce CLI fails on Node 20).
Install tools ....... Installs @salesforce/cli and the sfdx-git-delta plugin.
Authenticate ........ Logs in to the target org from the secret
                      TARGET_ORG_SFDX_AUTH_URL, alias targetOrg.
Generate delta ...... sf sgd source delta compares the pull request's base
                      commit with the merge commit, only under
                      demoDeployTest/force-app. Produces package.xml
                      (added/changed) and destructiveChanges.xml (deleted).
Decide test level ... No Apex changed: NoTestRun.
                      Changed classes ending in "Test": RunSpecifiedTests
                      with those classes.
                      Other Apex changes: RunLocalTests.
Dry run ............. sf project deploy start --dry-run from demoDeployTest.
                      Deletions are included only if there are any.
Deploy .............. Same command without --dry-run. Runs only if the dry
                      run passed.
Nothing to deploy ... If no Salesforce files changed, logs that and stops.
Upload artifact ..... Saves the manifests as the "delta-manifests" artifact.

Other settings
- Runs one at a time, so two merges never deploy at the same time.
- Uses the GitHub environment TargetDemoOrg. Required reviewers can be added
  there to approve each deployment.
- The comparison starts from the pull request's base commit, so components
  merged by other pull requests in the meantime may be deployed again. This
  is harmless and works for merge, squash and rebase merges.

7. EVERYDAY USE
---------------
Ship a change
  1. Create a branch from main; change files under demoDeployTest/force-app.
  2. Push and open a pull request into main.
  3. Merge it. The workflow validates and deploys only what changed.
  4. Watch it on the Actions tab, or with "gh run watch".

Useful commands (run sf commands from demoDeployTest/)

  Log in to an org:
    sf org login web --alias TargetDemoOrg --instance-url https://trailsignup-ad38b27e4f5ccb.my.salesforce.com

  Retrieve what the manifest lists:
    sf project retrieve start --manifest manifest/package.xml --target-org deployDemoTest

  Deploy by hand:
    sf project deploy start --manifest manifest/package.xml --target-org TargetDemoOrg --test-level RunSpecifiedTests --tests BedrockRequestPriorityServiceTest

  Refresh the GitHub secret (never shows the URL):
    sf org auth show-sfdx-auth-url --target-org TargetDemoOrg --no-prompt --json \
      | python3 -c "import sys,json;print(json.load(sys.stdin)['result']['sfdxAuthUrl'])" \
      | gh secret set TARGET_ORG_SFDX_AUTH_URL --env TargetDemoOrg --repo svk-sf-arch/deploy-test-poc

  Run the Apex tests in the target org:
    sf apex run test --class-names BedrockRequestPriorityServiceTest --target-org TargetDemoOrg --code-coverage --wait 10

  Watch workflow runs:
    gh run list --workflow deploy-on-merge.yml --repo svk-sf-arch/deploy-test-poc
    gh run watch --repo svk-sf-arch/deploy-test-poc
